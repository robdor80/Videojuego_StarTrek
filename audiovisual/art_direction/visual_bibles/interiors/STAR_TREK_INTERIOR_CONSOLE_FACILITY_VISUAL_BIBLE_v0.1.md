# STAR TREK — INTERIOR / CONSOLE / FACILITY VISUAL BIBLE v0.1

**Status:** FOUNDATION APPROVED FOR PROCEDURAL TESTING
**Inherits:** STAR_TREK_GLOBAL_VISUAL_BIBLE_v0.1

## Prime rule

> **Operational design first; visual era skin second.**

A console exists because an operator must perform defined actions.
A room exists because the ship/facility requires a real function.

## Resolution stack

`era → operator/organization → platform/facility design → room/station function → installed systems → access/alert/damage state → local lighting`

## Consoles

Visual layout must support the functional menu/action model.

Do not:
- add buttons merely to resemble Star Trek;
- use LCARS as a substitute for interaction design;
- expose controls the station does not have;
- show information the operator is not authorized/able to obtain.

The same functional console may receive different era/operator visual skins.

## Rooms

Room geometry and furnishings follow:
- role;
- capacity;
- installed systems;
- access;
- safety;
- traffic flow.

Unknown spaces are not invented as canon.

## Facilities

Starbases, stations, shipyards, outposts and planetary facilities must communicate:
- purpose;
- operator;
- technology;
- logistics/traffic;
- security/access;
- maintenance state.

## State

Alert lighting, smoke, damage, evacuation markings, exposed cabling or emergency equipment require current-state cause.

Repair removes temporary damage state while preserving history.

## Camera

For gameplay-reference images, prioritize:
- station visibility;
- line of sight;
- access routes;
- usable spatial understanding;
- player's likely POV where defined.
