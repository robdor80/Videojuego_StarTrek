# F11-P05-A02-03 — Preparación segura del Host institucional de Personal de Flota

**Fecha:** 11-11-2026  
**Estado de esta entrega:** CONTRATO Y GUARDAS ESTÁTICAS, NO HOST DE PRODUCTO IMPLEMENTADO.  
**Dependencias cumplidas:** primer ascenso 1101→1102 de #106; certificación A02-02 de #107 fusionada en `main`.  
**Frontera:** conservar el código nativo auditado y las seis campañas históricas. No tocar CoreRPG, F04/F05/F11 C++, las huellas, los oráculos, los pins ni `ESTADO_GLOBAL.json`.

## 1. Por qué no se debe conectar el emisor de ensayo

El primer ascenso es genuino en Core: identidad, comisión, autorización, evaluación, orden, evento `promotion`, cambio de rango, guardado y reintento viven en el mismo `WorldState`. Pero los antecedentes de ese escenario fueron creados por `f11_bootstrap_authorized_trial`, compilado **solo** en `TrekF11TrialHost` bajo `F11_NATIVE_TEST_HOST`. La biblioteca de producto **no puede emitir una comisión, concesión institucional ni aprobación**; solo comprueba hechos preexistentes y confirma la promoción.

La raíz histórica utiliza el marcador de ensayo `CAUSE=110501`. **No es una clave secreta, firma ni prueba de autenticidad.** Su presencia es compatible con la validación de los archivos del ensayo, pero un Host de producto no debe aceptarla como credencial de un cliente. El checksum Core comprueba corrupción accidental: no autentica que un guardado externo haya sido expedido por Flota.

**Decisión A02-03:** no publicar un endpoint `create_grant(actor_id, verified=true)`, ni copiar el bootstrap de pruebas a Unreal, ni fingir una promoción de producto mediante un archivo `.f04` elaborado por el jugador.

## 2. Propietarios estrictos de autoridad

| Operación | Propietario real futuro | Prohibido |
|---|---|---|
| Autenticar partida y procedencia de guardado | Host nativo de producto | Aceptar guardados externos sin política de autenticación |
| Identidad de 128 bits y comisión | Host de Flota, con hecho de graduación y orden | Asignar 1101 al crear cualquier NPC |
| Concesión de Personal de Flota | Servicio institucional privado y competente | Que la emita un capitán por rango, una consola o una IA |
| Evaluación y orden aprobada | P05-B1 + autoridad institucional verificable | Campo `verified` declarado por cliente |
| Ejecutar 1101→1102 | `f11_commit_promotion` y `WorldState` | Modificar directamente `RANK` o inventar expediente lateral |
| Presentar la noticia | P05-C/D, desde el hecho confirmado | Que una escena o un LLM conceda el grado |

La autorización de una orden institucional necesita procedencia, sujeto, competencia, ámbito, ventana temporal, revocación y causa. La decisión jurídica `effective_at` y la comunicación futura `presented_at` son hechos distintos; la segunda no bloquea la primera.

## 3. Arquitectura de implementación posterior (no ejecutada)

1. **Frontera de entrada del Host.** Inventariar el Host UE nativo que sea realmente propietario de las sesiones, su origen de identidades, el almacenamiento de saves y la política de archivos confiables. No asumir que `F04Ref`, una sesión local, una contraseña incrustada ni un `caller_id` suministrado por el usuario autentican nada.
2. **Emisión privada.** Diseñar una dependencia institucional accesible solo desde el Host de confianza, no desde Blueprint/console/PADD/LLM; recibir autoridad de una identidad autenticada de Flota y crear en `WorldState` la graduación, orden de comisión, comisión, concesión, evaluación y orden como hechos verificables. No reutilizar el marcador `110501` como nuevo sello de producto.
3. **Integridad y ciclo de vida.** Guardar en el mismo Core; validación fail-closed de procedencia, emisión, caducidad, revocación y carga. La persistencia local controlada por el Host necesita una política verificable de origen; no llamar cifrado al checksum.
4. **Operación inicial mínima.** Crear un oficial realmente comisionado en producto, comprobar que el capitán no hereda competencia de ascensos y confirmar **solo** 1101→1102 mediante la API nativa existente. Reintentos exactos devuelven recibo; claves reutilizadas con otros datos deniegan sin mutación.
5. **Pruebas y aceptación.** Probar denegaciones suplantadas, revocación anterior y en el mismo tick, carga en otro proceso, legado, F04/F05, MSVC/GNU, seis campañas y aceptación UE NullRHI/D3D12 en MSI. Ninguna escena ni control de juego puede fabricar un ascenso.

**Bloqueo objetivo:** sin conocer y comprobar la implementación real del Host y su almacenamiento confiable no sería responsable abrir esa vía de emisión. Este documento no convierte el ensayo en autoridad de producto.

## 5. Criterio de cierre y estado maestro

**Se puede aceptar esta entrega como `A02-03_PREPARACION`** si pasan las quince comprobaciones nuevas y la suite F11 offline, queda claro que el producto aún no emite autoridad y la PR no modifica las fuentes auditadas. **No equivale a `A02-03_HOST_REAL_COMPLETADO`.** Para ese cierre se necesitan HOST_01–HOST_07, código Host nativo revisado, CI Core y validación UE sobre el MSI.

La F11 global sigue **PLANIFICADA**. El primer ascenso nativo continúa certificado por A02-02; los destinos, sucesiones, transbordos, demás grados y comunicaciones diegéticas permanecen en P05-B/C/D/E. La [issue #104](https://github.com/robdor80/Videojuego_StarTrek/issues/104) continúa abierta.
