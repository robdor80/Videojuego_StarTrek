## 2. Fronteras vinculantes

`Unreal/UI/IA → HOST → F04/F05 → CoreRPG`. CoreRPG posee estado, reloj, RNG, hechos y reglas; H04 posee la publicación durable; HOST posee acceso, coordinación de sesión y enrutamiento. Nunca crear otra campaña activa, otra cola propietaria de Core ni un WorldState alternativo.

- Una intención de un cliente **no incluye identidad/autoridad aceptable por sí misma**. La referencia `F04Ref` del jugador debe resolverse en la sesión vinculada `BOUND`, dentro del hilo propietario y en la generación válida; `current_player` es solo una proyección.
- En comandos F05, no confundir **emisor autorizado** con **destinatario que acepta/ejecuta**. La orden la emite el jugador vinculado cuando el dominio lo permite; recepción y ejecución corresponden al destinatario real autorizado por F05. Para M0 el banco de prueba nativo podrá ejercer el rol de destinatario por una vía **interna de confianza, solo de test**, sin publicar un setter arbitrario de actor para UI/LLM/Blueprint/NPC. No crear en producto una identidad NPC simulada ni permitir suplantación.
- Respetar todas las precondiciones y resultados de F04/F05: ámbito, competencia, revisión, idempotencia, causa, plazo y estado de orden. No inferir competencia por rango o por `cause`; el HOST solo aplica controles de frontera y deja el veredicto final al dominio.
- Queda **prohibido** usar `TrekF11TrialHost`, incorporar `f11_trial_host.inc`, exponer `f11_commit_promotion` como emisor, otorgar destinos/rangos o interpretar permisos profesionales. F11-P05-A02-03 y su emisor son tarea del proyecto Star Trek principal. En H05 la operación institucional **no disponible** debe rechazarse sin mutar.
- Sin red, servidor, autenticación remota, UI UE, duplicación de serializadores o nuevos contenedores de archivos de partida.

## 3. Contrato lógico del despacho (sin fijar ABI antes de la implementación)

Petición interna de HOST: `{session_generation, correlation_id, operation, expected_core_revision?, domain_key?, cause?, payload}`; los campos de negocio se verifican contra la cabecera F04/F05 real. No son credenciales de usuario.

Los nombres lógicos propuestos se alinean con H01:

| Operación | Backend verificado | Regla de enrutamiento |
|---|---|---|
| `QUERY_VIEW` | `f04_stats`, `f04_handles`, `f04_person`; vistas F05 según observador | Solo lectura, observador resuelto en Core, respuesta filtrada |
| `F05_SUBMIT_ORDER` | `f05_submit` | Principal vinculado como emisor; destinatario/estación de campaña revalidados por F05 |
| `F05_RECEIVE_ORDER` | `f05_receive` | Únicamente destinatario validado; no asumir que es el jugador |
| `F05_EXECUTE_ORDER` | `f05_execute_order` | Únicamente destinatario validado; un intento máximo; no auto-reintentar |
| `F05_CANCEL_ORDER` | `f05_cancel` | Actor real validado y reglas F05 |
| `F04_COMMAND` | `f04_execute` | Solo si se justifica en M0; no bypass de F05 para demostrar órdenes |
| `SAVE_SLOT/RESTORE_SLOT` | `SessionOwner::save/restore` de H04 | Nunca implementar IO alternativo |
| `F11_INSTITUTIONAL_COMMAND` | API de producto aún no aprobada | Fallo cerrado, sin fixture |

Codex determinará los tipos y firmas C++ finales con base en el código actual. Priorizar una extensión **aditiva y pequeña** del propietario `SessionOwner` y su `NativeSession`; no crear un coordinador paralelo. La lógica de F05 debe vivir en las API existentes. No cruzar `F04Session*`, objetos Core, excepciones ni credenciales al cliente ni a una ABI C ajena.

**Invariantes de admisión y concurrencia:**
1. Sin generación activa o con generación ajena/caducada → rechazo antes de tocar Core; respuesta y vistas vacías.
2. `UNBOUND`, `RESOLVING` e `INVALID` → rechazo de intenciones de jugador; no autovincular.
3. `SAVING/LOADING/CLOSING` → `BUSY_STATE` o caducidad conforme a H02/H04; tareas ya admitidas conservan orden o se invalidan según la política existente. No mantener bloqueado el mutex mientras se ejecuta Core.
4. Para cada acción: obtener/revalidar actor, revisión y ámbito en el trabajador propietario; delegar al dominio. Respuestas tardías se descartan si cierre/LOAD invalidó la generación, sin afirmar que se deshizo una mutación Core ya confirmada.
5. El `correlation_id` del HOST **no** sustituye `F05OrderRequest.key`. Repetición de misma key y mismo payload debe respetar idempotencia F05; misma key y diferente payload → conflicto. No cambiar keys a escondidas.
6. Una revisión caducada no provoca actualización y reejecución automática: devolver `REVISION_STALE` y requerir intención nueva. Un timeout exige consultar estado real de la orden; no ejecutarla de nuevo a ciegas.
7. Una respuesta Core aceptada no es sinónimo de guardado durable. Solo `save()` confirmado y válido acredita la persistencia H04.

## 4. Contrato de proyección mínima de solo lectura (H05-P03)

Definir una vista C++ nativa **pequeña y versionada por semántica**, no un JSON alternativo autoritativo. Proyección sugerida por consulta autorizada:

- `CampaignView`: generación/estado para correlación, revisión Core y reloj Core (`F04Stats.revision/now`), personaje PERSON vinculado (`F05PlayerBinding`), identificador de nave derivado de F04; **nunca** usar los campos como autorizaciones futuras.
- `OrderView`: ID de orden, estado y código de dominio, revisión y resultado de ejecución `F05Receipt/F05ResultView`, solo cuando `f05_order` / `f05_result` acepten al observador actual.
- En fallo: campo de error HOST; código F04/F05 original conservado en diagnóstico **interno** si existe; salida de vista vacía, sin eventos/campos de otro jugador. Tamaños acotados y paginación F04/F05 donde proceda.
- La lectura no cambia revisión, RNG, reloj ni número de eventos. Múltiples consultas sucesivas sobre estado estable producen la misma proyección. Un lector de otra generación o sin binding no recibe hechos.

**Decisión sobre implementación H05-P03:** ChatGPT deja el contrato y sus validadores conductuales especificados; **no se publica una implementación de proyección sin la interfaz C++ definitiva de H05-P01/P02**, para evitar un módulo huérfano o solapado con Codex. Codex implementará la mínima vista de producto necesaria para M0 y fijará sus nombres en el informe. ChatGPT auditará después las invariantes y preparará validadores livianos adicionales si la interfaz resulta estable.

## 5. Ciclo M0 de referencia (demostración nativa, no partida de Academia)

1. Abrir una campaña de población F04 controlada con `SessionOwner` y raíz privada de H04; obtener generación.
2. El test de confianza vincula **una persona existente legítima** mediante `PlayerBootstrap`; para el escenario positivo elegir un sujeto con autoridad real de F05 según los fixtures. **No** presentar al capitán sintético como personaje definitivo del jugador ni fabricar cadetes.
3. Leer vista de estado: mismo Core, sesión, observador vinculado y revisión real.
4. Emitir una orden F05 `F04_SCAN` con key/cause/plazo/revisión válidos. Comprobar orden emitida, no ejecutada.
5. Desde el **receptor real** y en la frontera de confianza del ensayo, aceptar y ejecutar una sola vez; comprobar `F05ResultView` y la cadena de eventos/transacciones Core, sin atribuir contactos de sensores.
6. Guardar la ranura mediante H04. Cerrar y reabrir en **otro proceso** con `restore`. Confirmar campaña, binding, resultado, cronología, revisión, estado de orden y consumo RNG persistidos, sin mutaciones ocultas de LOAD.
7. Reconsultar vía API de solo lectura de HOST tras LOAD; comprobar que la generación vieja no abre ni muta la nueva campaña. Repetir la misma key/payload F05 desde sesión nueva, si el contrato F05 lo admite, y comprobar que no aparecen efectos adicionales.
8. Escenarios negativos independientes: jugador sin vínculo, revisión vieja, scope cruzado, permisos F05 insuficientes, clave reutilizada con otro payload, intento desde otra generación, cierre concurrente y SAVE durante despacho. No destruir una partida buena ante un error.

La recuperación entre procesos ya existe en H04, pero **el recorrido completo con una intención de juego en H05 es nuevo** y permanece NO PROBADO hasta CI.
